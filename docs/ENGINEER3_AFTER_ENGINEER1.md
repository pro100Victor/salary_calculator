# Инженеру 3: подключение готовой части инженера 1

Этот документ уточняет прежний LAB4_ENGINEER3_HANDOFF.md. ORM, мапперы и SQL-репозитории уже реализованы; не создавайте параллельно вторые версии тех же классов.

## Что уже готово

- Единственный Base: `salary_calculator.db.base.Base`.
- Восемь таблиц: импорт `salary_calculator.db.models` регистрирует их все.
- ER: docs/ER.md и docs/ER.svg. Ограничения, каскады и many-to-many описаны там.
- SQL-репозитории: SQLAlchemyOrganizationRepository, SQLAlchemyPositionRepository, SQLAlchemyNormRepository, SQLAlchemyEmployeeRepository, SQLAlchemyTimesheetRepository, SQLAlchemyStatementRepository. Каждый принимает Session, не выполняет commit/rollback.
- Готовая сборка: `build_sql_services(session)` из `salary_calculator.application.sql_services`.
- Сервисы уже явно сохраняют mutable-табель. ID сотрудника назначает SQL-хранилище. Реквизиты, тарифы, ручные нормы, снимки ведомости поддерживают постоянное хранение.

## Шаг 1. Настройки и подключение

1. Добавьте `uv add "psycopg[binary]"` и закоммитьте pyproject.toml/uv.lock.
2. Подготовьте `db/settings.py` и `db/session.py`: DATABASE_URL из окружения, PostgreSQL Engine с pool_pre_ping, sessionmaker. Не создавайте таблицы при импорте.
3. Формат URL: postgresql+psycopg://user:password@db:5432/salary в Compose, localhost вместо db при работе с хоста.
4. Подготовьте .env.example; настоящие пароли и .env не коммитить.

## Шаг 2. Alembic

1. Выполните `uv run alembic init migrations`.
2. В env.py подключите метаданные всех моделей. Минимальный вариант:

```python
from salary_calculator.db.models import OrganizationRow

target_metadata = OrganizationRow.metadata
```

Это тот же объект Base.metadata: импорт пакета db.models/__init__.py уже зарегистрировал все восемь таблиц. Не создавайте ещё один Base. Добавьте src в путь импорта через конфигурацию Alembic (`prepend_sys_path`), а не меняйте все импорты на src.salary_calculator.

3. На пустой PostgreSQL выполните `uv run alembic revision --autogenerate -m "create salary schema"`.
4. Проверьте начальную миграцию: 8 таблиц, первичные и внешние ключи, INTEGER/SERIAL, Text, Date, Numeric, UNIQUE/CHECK, индексы и ondelete.
5. Условие ASCII-цифр намеренно выражено переносимыми replace/length. Не теряйте его при переносе CHECK. Временный ID сотрудника не должен становиться server_default=0.
6. Выполните `uv run alembic upgrade head`, current/history, alembic check. Проверьте downgrade/upgrade в отдельной тестовой БД.
7. Base.metadata.create_all() не используйте ни в приложении, ни в production-тестах. Не заменяйте ревизию динамическим созданием таблиц при старте приложения.

Тесты инженера 1 создают только временную SQLite-схему программными операциями Alembic для быстрой проверки репозиториев. Это не production-миграция и не доказательство выполнения upgrade head на PostgreSQL.

## Шаг 3. SQLServiceProvider

Реализуйте `application/sql_provider.py`, наследник существующего ServiceProvider. В __init__ примите SessionFactory; storage_mode возвращает PostgreSQL.

Алгоритм operation():

1. Открыть Session: `with session_factory() as session:`.
2. Открыть транзакцию `with session.begin():`.
3. Выдать `yield build_sql_services(session)`.
4. Успешный выход коммитит транзакцию, исключение откатывает. Session закрывается в любом случае.
5. IntegrityError после отката преобразовать в безопасную прикладную ошибку. Для UNIQUE ИНН желательно ValueError с понятным сообщением о повторном ИНН; не раскрывать SQL/параметры пользователю.
6. Остальные инфраструктурные SQLAlchemyError после отката преобразовать в StorageError. Обычные ValueError/LookupError и HTTPException не подменять StorageError.
7. Логировать техническую причину инфраструктурной ошибки на сервере. Не использовать голый except и не продолжать запросы в сломанной транзакции.

В tests/support/sql_provider.py есть тестовый пример алгоритма. Его storage_mode, сообщения и настройки относятся только к SQLite-проверкам; не подключайте тестовый модуль к рабочему приложению.

При отказе БД нельзя незаметно переключаться на InMemory. Иначе пользователь подумает, что сохранил данные в PostgreSQL, а после перезапуска они исчезнут.

## Шаг 4. Общая factory

Измените application/factory.py: create_provider() возвращает ваш SQLServiceProvider с SessionFactory. Если нужен выбор режима, сделайте его явным через STORAGE_BACKEND=postgres/memory. Для сдачи основной путь должен запускаться с PostgreSQL.

Больше ничего в frontend менять не требуется. CLI и веб уже вызывают общую create_provider(), а HTTP-dependency завершает операцию до отправки успешного ответа. Если меняете публичные методы, ответственность за обновление их вызовов остаётся на вашей интеграции.

## Шаг 5. Compose и образ

- Сервис db: PostgreSQL с named volume и healthcheck.
- Сервис migrate: ждёт здоровую БД, выполняет alembic upgrade head из того же образа, завершается успешно.
- Сервис web: ждёт успешных миграций, получает DATABASE_URL, публикует 8000.
- Скопируйте src и frontend в образ с тем же относительным расположением; также pyproject.toml/uv.lock и файлы Alembic.
- В контейнере запускайте:

```bash
uv run uvicorn --app-dir src --factory salary_calculator.web.app:create_web_application --host 0.0.0.0 --port 8000
```

src/web_main.py слушает 127.0.0.1 для локальной разработки, поэтому не используйте эту привязку внутри контейнера без изменения команды запуска.

CLI документируйте отдельной командой/Compose-профилем с stdin/TTY. Не запускайте интерактивный CLI как обычный фоновый демон.

## Шаг 6. Блокировки и ограничения

SQLAlchemyTimesheetRepository.get()/save(), сохранение нормы и ведомости используют одну строку периода как общий ресурс блокировки. Постоянная Session на весь CLI недопустима: одна Session на одну пользовательскую команду или HTTP-запрос. Не начинайте вторую независимую транзакцию в репозитории.

ensure_period() сначала пытается заблокировать существующий период. Если периода ещё нет, блокирует единственную организацию, повторно проверяет наличие периода и создаёт его. Для сохранённого периода порядок не требует повторного захвата организации. Это уменьшает риск взаимной блокировки разных путей записи.

Проверьте на настоящей PostgreSQL двумя Session: заполнение против закрытия, два одновременных формирования, норма против формирования. SQLite не проверяет FOR UPDATE. При deadlock/serialization failure откатите операцию и верните понятное сообщение; не повторяйте произвольные команды автоматически без оценки их идемпотентности.

Редактирование текущей карточки не переписывает снимок старого листка. В UI признак устаревания ведомости по-прежнему относится к версии табеля; новые правила автоматического перерасчёта из-за изменения карточки в этом этапе не вводились.

## Шаг 7. Обязательная финальная проверка без возвращения к инженеру 2

1. Установить зависимости, поднять чистую БД через Compose, применить миграцию.
2. Пройти весь сценарий веба: организация → тариф → сотрудник → норма → табель → строки → ведомость → листок → перерасчёт → закрытие.
3. Проверить ту же информацию в CLI.
4. Перезапустить процессы приложения и PostgreSQL без удаления volume; убедиться, что все настройки, записи и закрытие сохранились.
5. Проверить неверный ввод, повторный ИНН, превышение нормы, закрытый период. Следующая корректная операция после ошибки должна работать.
6. Проверить отказ БД/rollback, отсутствие частичной ведомости, отдельные Session запросов и отсутствие DetachedInstanceError.
7. Прогнать существующие 29 тестов и дополнительные PostgreSQL-тесты. Создание PostgreSQL-схемы в них — только через Alembic.
8. Сверить все 7 критериев лабораторной. Обновить README только после фактической работы PostgreSQL: команды, миграции, ER и режим хранения.

Не описывайте PostgreSQL и Docker как уже проверенные по результатам SQLite-тестов инженера 1. Итоговую проверку работы интерфейса и необходимые исправления совместимости выполните в рамках своей интеграции совместно с инженером 1; менять frontend ради способа хранения не требуется.
