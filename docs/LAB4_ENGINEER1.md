# Лабораторная работа 4 — инженер 1

## Результат и границы работы

Подготовлена предметная SQL-часть на основе актуального salary_calculator.zip: ER-схема, восемь ORM-классов, восемь классов-мапперов, SQL-реализации репозиториев и адаптация существующих сервисов. Состав полей форм, HTTP-пути и форматы ответов сохранены. Frontend и CLI переписывать для этих изменений не требуется.

SQL-репозитории принимают внешнюю Session. Сборка `build_sql_services(session)` готова для вызова из SQLServiceProvider инженера 3. Текущая `application/factory.py` пока продолжает возвращать InMemoryServiceProvider. Это явно означает: копирование данного комплекта само по себе не переключает рабочий веб-сервер на PostgreSQL.

Инженер 3 завершает SessionFactory, SQLServiceProvider, Alembic env/revision, Compose и фактический PostgreSQL-прогон. Новые тесты инженера 1 подставляют тестовый провайдер в существующие CLI и HTTP-приложение и проверяют реальную запись SQLAlchemy в SQLite. Не называйте весь комплект завершённой ЛР4 до интеграции инженера 3.

1. Откройте `engineer1_lab4_update.zip`. Пути внутри архива начинаются от корня вашего проекта.

7. Добавьте `application/sql_services.py`.
8. В `src/main.py` исправлен только порядок импортов Ruff. Можно взять полный файл из комплекта либо самостоятельно выполнить `uv run ruff check src/main.py --fix`.

Все перечисленные изменения совместно образуют одно обновление. Не запускайте промежуточную сборку, когда сервис уже вызывает repository.add(), а старый файл EmployeeRepository ещё не обновлён.

## 3. ORM и мапперы по файлам

| db/models | Класс таблицы | Соответствующий mapper в db/mappers |
| --- | --- | --- |
| organization.py | OrganizationRow | OrganizationMapper |
| position.py | PositionRow | PositionMapper |
| employee.py | EmployeeRow | EmployeeMapper |
| period.py | PeriodRow | PeriodMapper |
| timesheet.py | TimesheetRow | TimesheetMapper |
| timesheet_entry.py | TimesheetEntryRow | TimesheetEntryMapper |
| payroll_statement.py | PayrollStatementRow | PayrollStatementMapper |
| payroll_result.py | PayrollResultRow | PayrollResultMapper |

Domain-классы Employee, Organization и остальные остаются dataclass. Валидаторы, в том числе единый Employee.validate_dates(), остаются в них. ORM отвечает за структуру таблиц и ограничения. Mapper.to_domain() создаёт предметный объект, а apply() переносит его поля в ORM-запись. Session, commit и HTTP-коды не являются ответственностью маппера.

В моделях SQLAlchemy используются Mapped/mapped_column, PK/FK, relationship/back_populates. Взаимные типы импортируются под TYPE_CHECKING, чтобы аннотации не создавали циклический импорт. `db/models/__init__.py` регистрирует все таблицы для реальных отношений и Alembic.

Схема и все ограничения: `docs/ER.md`. Графическая версия: `docs/ER.svg`, исходник Graphviz: `docs/ER.dot`. На SVG показаны поля, ключи и кратности; текст ER.md содержит полный список UNIQUE/CHECK и объяснение каскадов.

## 4. Что изменилось в существующих методах

### services/organization.py

`__init__(repository=None, positions=None)` теперь принимает хранилища реквизитов и тарифов. Если аргументы не переданы, использует InMemory, сохраняя прежний способ сборки.

`set_organization()` создаёт проверенный Organization и вызывает repository.save(). `get_organization()` читает хранилище. Методы set_position/get_position/list_positions используют PositionRepository. Формула rate_for(), делегирующие validate_* и публичные имена методов сохранены.

### services/calendar.py

`__init__(repository=None)` получает NormRepository. `set_norm()` после прежней проверки сохраняет норму. `get_norm()` сначала читает ручное значение, иначе считает будни по прежнему правилу, без производственных праздников.

SQL-норма после формирования табеля не меняется: SQLAlchemyNormRepository проверяет это под блокировкой периода. Интерфейсы сохраняют существующий предварительный запрет.

### services/employee.py

`add_employee()` больше не определяет max(employee_id)+1. Создаёт проверенную карточку с временным ID=0 и передаёт её repository.add(). Возвращается Employee с настоящим ID хранилища.

В PostgreSQL ID назначается последовательностью при INSERT/flush; значение 0 не записывается как первичный ключ и не возвращается пользователю. InMemory-реализация назначает локальный ID внутри своего репозитория. Внешние методы add/update/dismiss/get не переименованы.

### repositories/employee.py

В ABC добавлен add(employee) -> Employee, реализованный обеими реализациями. save() по-прежнему обновляет карточку. SQL-версия находит должность через FK и читает её вместе с карточкой, не заставляя интерфейс работать с ORM.

### services/timesheet.py

`fill()` теперь явно вызывает repository.save(timesheet) после изменения entries/revision. `close()` явно сохраняет closed. Без этих вызовов изменение самостоятельного dataclass не попадало бы в SQL-БД.

### repositories/timesheet.py

SQLAlchemyTimesheetRepository сохраняет заголовок, всех участников и строки. При чтении возвращает новый Timesheet. Незаполненные строки входят в employee_ids, но не входят в entries. Для PostgreSQL операции координируются блокировкой периода. Добавлены проверки закрытия, зафиксированной нормы, состава и устаревшей версии перед сохранением.

### repositories/statement.py

SQLAlchemyStatementRepository сохраняет заголовок и все результаты в той же внешней транзакции. При перерасчёте обновляет строки по employee_id, не создавая конфликтующих дубликатов UNIQUE. Хранит снимок Employee, а не только ссылку на текущую карточку.

`PayrollService` и расчётные стратегии не требовали изменения: они уже сохраняют результат через StatementRepository. Формулы зарплаты и НДФЛ не копировались в репозитории или JavaScript.

## 5. Инварианты схемы и поведения

- Одна организация на установку: id=1 с CHECK. Универсальность означает настраиваемые тарифы и реквизиты, а не несколько изолированных кабинетов предприятий.
- ИНН/КПП хранятся текстом. Ведущие нули сохраняются.
- Должность ищется по strip().casefold(), ключ уникален внутри организации.
- Стаж от 0 до 80, ставка положительная, даты увольнения/приёма упорядочены.
- Денежные значения Numeric(20,2) и Decimal. Процент надбавки — Numeric без фиксированного масштаба для сохранения допустимой точности PostgreSQL.
- Табель содержит всех участников даже до ввода смен. Три NULL — незаполненная строка, три нуля — заполненная строка.
- Норма проверяется относительно календаря сервисом; сумма дней относительно нормы — моделью и сервисом перед записью. CHECK защищает локальные поля, но не имитирует межтабличный запрос.
- Сохраняются revision, source_revision и closed; интерфейс после перезапуска узнает устаревшую ведомость и закрытый период.
- Кадровые записи не удаляются при увольнении. FK RESTRICT защищает историю. CASCADE/delete-orphan применяется только к дочерним строкам владельца.
- Старый листок использует снимок названия организации, ФИО, ИНН, должности, дат, стажа и ставки. Изменение текущей карточки его не переписывает.

## 6. Импорты и совместимость интерфейсов

Существующие `salary_calculator.models.*` и пути HTTP-обработчиков не менялись. Новые SQL-реализации импортируются из тех же файлов репозиториев, где находится их ABC. Общая SQL-сборка импортируется так:

```python
from salary_calculator.application.sql_services import build_sql_services
```

В SQL-провайдере внутри открытой транзакции вызывается `yield build_sql_services(session)`.

Веб и CLI продолжают получать ApplicationServices. Не добавляйте ORM-объекты в API-ответы. Имена JSON-полей, формат дат YYYY-MM-DD, строковые денежные суммы, employee_id, position и status сохраняются. Сервер возвращает рассчитанную ставку; JavaScript её не считает.

Новых библиотек для части инженера 1 добавлять не пришлось: SQLAlchemy и Alembic уже находятся в pyproject.toml/uv.lock. Эти файлы не включены в обновление. Драйвер psycopg добавляет инженер 3 при подключении PostgreSQL.

## 7. Как проверить после переноса

Из корня проекта:

```bash
uv sync
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

Только новые SQL-проверки:

```bash
uv run pytest tests/test_sql_backend.py -v
```

Фактически пройдены 29 тестов: 21 существующий и 8 новых SQL-проверок. Ruff check и format --check проходят. Предупреждение Starlette о будущем переходе с httpx на httpx2 осталось от прежнего тестового окружения; оно не является провалом тестов.

Новые проверки выполняют настоящие INSERT/UPDATE/SELECT SQLAlchemy на временном SQLite-файле. Схема тестов создаётся через программный Alembic autogenerate и Operations; Base.metadata.create_all() не применяется. Это не заменяет полноценные production-файлы revision/env.py и команды alembic upgrade head, которые готовит инженер 3.

Проверены новые Session и новый Engine, сохранность закрытого периода, снимки после изменения карточки, rollback после flush, перерасчёт, различие нулевой и пустой строки, FK/CHECK, many-to-many, существующие CLI и HTTP с SQL-провайдером. PostgreSQL-DDL успешно компилируется. Реального сервера PostgreSQL в этой проверке нет; FOR UPDATE и конкурентные запросы на PostgreSQL должен проверить инженер 3.
